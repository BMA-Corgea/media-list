## Upstream facts confirmed by reading the APIs, not from memory

- **TMDB `search/multi`** returns `media_type` per result, `genre_ids`, and `origin_country`
  on tv results only; movies carry `original_language` instead. AC2's rule therefore has to
  accept **either** signal, which is why it is written as an OR.
- **TMDB `external_ids`** is a separate call per title — `search/multi` does not carry
  `imdb_id`. So AC4's details endpoint is genuinely a second round trip, not an oversight.
- **Image paths** come back as `/abc.jpg` fragments needing a size-prefixed base
  (`image.tmdb.org/t/p/w500`). The API does not return usable URLs.
- **AniList** is a POST GraphQL endpoint at `graphql.anilist.co`, no key, and it matches on
  title search — there is no TMDB→AniList id mapping, so anime enrichment is a fuzzy title
  match and must be allowed to return nothing without failing the request.
- **IGDB** is POST-with-a-body-query (apicalypse), needs `Client-ID` + `Authorization:
  Bearer`, and cover art comes back as an `image_id` that must be templated into
  `images.igdb.com/igdb/image/upload/t_cover_big/<id>.jpg` — portrait, which is the whole
  reason it was chosen over RAWG.

## Risks

1. **AniList matching is fuzzy and can be wrong.** Enrichment must never overwrite a TMDB
   title with an AniList one on a weak match — it decorates, it does not replace.
2. **A search that fans out to two APIs plus image downloads can be slow.** Evan explicitly
   deprioritised speed on repo-tour; here it still matters because search is typed-into.
   Images must **not** be downloaded during search — only on add (T-4) or on details.
3. **The token cache is a file in `data/`.** It must be created with restrictive permissions
   and must never be committed; `data/` is already ignored, and the file needs `0600`.
