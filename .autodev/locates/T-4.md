# T-4 — Locate

| What exists | Where | How T-4 uses it |
| --- | --- | --- |
| `/api/search`, `/api/details/{source}/{id}` | `backend/main.py` (T-3) | The whole capture path. T-4 adds no source code of its own. |
| `cache()` | `backend/artwork.py` (T-3) | Already called inside `/api/details`, so a stored row's paths are local before T-4 sees them. |
| `titles` table | `backend/schema.sql` (T-2) | Every column T-4 writes already exists — `detail` is the JSON column that will carry `media_type`. |
| `execute()` / `query()` | `backend/db.py` (T-2) | Writes. `execute` returns `lastrowid`. |
| `.card`, `.poster`, `.field`, `.btn`, `.chip`, `.empty` | `frontend/src/skins/base.css` (T-2) | The add view must use these and declare **no colours of its own**, or an alternate skin stops covering it. |
| `#app` + `main()` | `frontend/src/main.js` (T-2) | Currently renders a topbar and an empty state. T-4 replaces the body with a real view. |

## Constraints found

1. **`sqlite3.IntegrityError` is the duplicate signal** — the unique index from T-2 is on
   `(source, source_id)`. Catching it is race-safe; a `SELECT` first is not.
2. **`db.execute()` opens its own connection per call**, so "insert then read back the row"
   is two connections. Fine at this scale, but the insert must return enough to render.
3. **`detail` is TEXT holding JSON** — T-3's details response already carries a `detail`
   object; `media_type` has to be merged into it, not stored in a new column.
4. **No client router exists yet.** T-5 and T-6 both need one. T-4 introduces the minimum
   (a hash route + a render switch) rather than leaving each later ticket to invent its own.
