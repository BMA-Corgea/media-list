# T-10 — CSV export and the resolver import

**Type** feature · **Risk** HIGH (bulk writes into Evan's data) · **Intent** T-1 · **After** T-7

Evan has **no existing list** and intends to generate one with a chatbot. So the input is
loose by design, and the importer is a **resolver**, not a loader. The README already
publishes the contract; this ticket must honour it exactly.

## Acceptance criteria

1. **AC1 — export is full fidelity.** Columns exactly as the README:
   `title,year,kind,why,status,stars,queue_position,tmdb_id,imdb_id,added_at,watched_at,review`
   RFC4180 quoting, UTF-8.
2. **AC2 — export re-imports exactly.** Export → import → **no changes, no duplicates**: the
   round-trip is the acceptance evidence.
3. **AC3 — the README's starter CSV imports cleanly**, including its quoted field and its
   trailing-empty-`why` row.
4. **AC4 — loose input resolves.** `title` alone is enough. Rows are searched, candidates
   returned **with posters** for the ambiguous ones.
5. **AC5 — nothing is guessed silently.** A row with several plausible matches comes back
   **needing a choice**; a row with none comes back **unmatched**. Neither is dropped.
6. **AC6 — nothing is written until the whole thing is confirmed.** Preview and commit are
   separate calls.
7. **AC7 — the commit is atomic.** A failure part-way leaves the database **untouched** —
   proven by forcing a failure mid-commit and showing the row count unchanged.
8. **AC8 — `tmdb_id` skips the search.** A row carrying one resolves without a lookup; that
   is what makes AC2 exact rather than approximate.
9. **AC9 — duplicates are not re-added.** A row already on the list is reported as such.
10. **AC10 — import appends gap-tolerantly** (`MAX+10`), preserving T-7's scheme, and does
    not resurrect a `seen` row into the queue.
11. **AC11 — the file never leaves loopback**, and exports are gitignored.

## Out of scope
Pexels chrome (T-11).
